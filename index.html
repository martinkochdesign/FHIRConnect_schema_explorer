FHIRConnect schemas at a glance

FHIRConnect describes mappings between openEHR and HL7® FHIR® in YAML files. Two kinds of files work together: model mappings (one archetype ⇄ one FHIR resource/profile) and context mappings (one openEHR template ⇄ one FHIR profile, orchestrating several model mappings). Use the tabs to browse each schema as a tree, or search across both from the header.

Model

Model mapping schema

Files with type: model or type: extension. Defines element-level mapping rules, conditions, nested and referenced mappings.

schema elements

Context

Context mapping schema

Files with type: context. Binds a FHIR profile to an openEHR template and lists which model mappings are used and where the transformation starts.

–
schema elements

How the two file types fit together

Context mapping (type: context)

  • context.profile.url → FHIR profile
  • context.template.id → openEHR template
  • context.archetypes[] → model mappings to use
  • context.extensions[] → extensions to apply
  • context.start → entry archetype
→

Model mapping (type: model)

  • spec.openEhrConfig.archetype ⇄ spec.fhirConfig.structureDefinition
  • preprocessor → model-level conditions / hierarchy
  • mappings[] → element rules (with.fhir ⇄ with.openehr)
  • slotArchetype → delegates slot content to another model
←

Extension (type: extension)

  • Same schema as model mapping
  • spec.extends → base model
  • mappings[].extension: add / append / overwrite
  • mappings[].appendTo → target rule

About this page

    

      
Purpose

      
This page is an unofficial, interactive learning aid for exploring the structure of the FHIRConnect v1.0.0 model mapping and context mapping JSON Schemas. It visualises the schemas as browsable trees, makes their elements searchable and adds explanatory texts to help readers understand FHIRConnect YAML files.

Observed schema notes

      
Points noticed while building this explorer. They are observations about the published schemas, not official errata.

      
    
        
        
  • mappings[].manual and manual[].openehr are typed as array but declare properties instead of items; validators therefore do not check the contents of array entries.
    • 
        
  • openehrCondition requires either targetAttribute or targetAttributes (oneOf); the corresponding fhirCondition has no such constraint.
    • 
        
  • unidirectional and operator are free strings in the schema – accepted values are defined only in the specification text.
    • 
        
  • The context schema does not mark profile.url or template.id as required, although they are the core of the binding.
